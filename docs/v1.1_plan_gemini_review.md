# v1.1 — Equipment Database + PPT Generator
## Gemini Architecture Review (2026-04-02)

---

## 1. v1.1 三个功能的优先级建议

**建议优先级：Equipment Database > PPT大纲自动生成 > PDF Proposal 整合**

### 核心理由（Grounding First）

站在"售前推进系统"而非纯粹"文档生成器"的角度看，**数据的准确性永远优于排版的精美度**。

在实际的复杂物流投标（例如汽车零配件中心仓的规划）中，不同设备（如重载 AGV 与轻型料箱机器人的有效载荷、速度、充电周期差异）会直接导致车队规模、Capex 和 Opex 的剧烈波动。

如果缺乏一个强类型的 Equipment Database，LLM 在生成 `core_solution` 或估算实施周期时极易产生幻觉，或者只能使用极为宽泛的描述。

**优先构建设备库，将具体的设备参数注入到 `workspace_manager` 的快照中，才能让生成的方案具备真正的工程级说服力。**

至于 PDF 和 PPT，它们只是底层数据的不同展现面，可以稍后完善。

## 2. Equipment Database 与 Scenario Engine 的架构关系

**结论：必须严格解耦，保持独立，但通过接口深度联动。切忌将它们合并。**

### Equipment Database（数据层 / Fact Store）

- **定位**：静态/半静态的客观事实库
- **职责**：回答"是什么"和"多少钱"
  - 例如：某型号 AMR 的最大速度是 1.5m/s，额定载重 500kg，单机成本 ¥X，MTBF
- **架构**：独立模块（关系型数据库或高度结构化的 JSON/YAML），支持版本控制（与 Assumption Governance 体系对齐）

### Scenario Engine（业务逻辑层 / Domain Logic）

- **定位**：动态的计算与推理规则库
- **职责**：回答"怎么算"和"需要多少"。封装了15种自动化场景的物理建模

### 联动方式：依赖注入（Dependency Injection）

当 `scenario_engine` 计算一个高密度存取场景时，向 Equipment Database 发起查询：

```python
get_equipment(type="Shuttle", specs={"throughput": ">100"})
```

拿到具体参数后，再结合用户输入的吞吐量假设，计算出所需的穿梭车数量和整体能耗。

## 3. PPT 大纲生成的替代方案

python-pptx 在处理复杂排版、自动对齐和动态内容溢出时确实非常痛苦，往往需要硬编码大量坐标，维护成本极高。

**首选方案：Markdown → Marp**

架构思路：让 `proposal_engine.py` 输出结构化的 Markdown 文件。通过在 Markdown 中加入简单的分隔符（`---`），结合 [Marp](https://marp.app/) 工具链，可以直接将其渲染为高质量的 PDF 幻灯片或导出为 PPTX。

**优势：**
- 开发成本极低
- LLM 非常擅长生成结构严谨的 Markdown
- 只需维护几套 CSS 主题即可控制所有幻灯片的视觉风格
- 完全摆脱了操作底层 XML 节点的折磨

**备选方案：JSON to 前端渲染库（Reveal.js / Slidev）**

如果未来前端是完整的 Web Dashboard，可以直接让后端输出包含幻灯片层级关系的 JSON，前端利用 Slidev 动态渲染。这比生成实体文件更符合 SaaS 体验。

## 4. 迈向"完整售前推进系统"的缺失拼图

完成 v1.1 之后，系统已具备强大的方案生成能力，但要真正成为主导售前周期的核心业务系统，还需要补齐以下高阶模块：

### Financial & ROI Modeler（商业定价引擎）

目前的参数库解决了成本基线问题，但售前还需要看**回报率**。

系统需要一个独立模块，将方案所需的设备清单、人工、场地租赁与折旧、资金成本（WACC）进行整合，自动生成多周期的现金流量表，计算**投资回收期（Payback Period）和内部收益率（IRR）**。

### ESG 与可持续发展测算模块（Sustainability Tracker）

绿色物流和脱碳目标在当前的中大型物流招标中已从加分项变成必选项。

系统应当能够基于 Equipment Database 中的设备能耗参数、库区规划、包装材料消耗，自动测算方案的**碳足迹（Carbon Footprint）**。能够一键输出符合 ESG 标准的减碳效益分析，将极大提升投标竞争力。

### Bid Scenario Version Diffing（方案沙盘推演与版本比对）

客户经常问："如果将一期的吞吐量预期降低 20%，同时把自动化率提高一档，对总成本有什么影响？"

Workspace 已有快照机制，下一步需要开发一个**对比引擎**，能够并排展示两个 Bid Session 的差异（底层参数、设备选型差异、最终报价对比），并让 LLM 自动生成"差异说明与影响分析"。

---

## 5. v1.1 推荐开发顺序

| Step | 模块 | 原因 |
|------|------|------|
| **Step 1** | Equipment Database | 是其他所有模块的数据基础，必须先建 |
| **Step 2** | Equipment → Workspace 注入 | 将设备参数注入快照，让 proposal_engine 能引用真实设备数据 |
| **Step 3** | PPT大纲生成（Marp/Markdown） | 低成本，用 LLM 生成 Markdown，用 Marp 渲染 PPTX |
