# v1.0 — Proposal Studio + Workspace
## Gemini Architecture Review (2026-04-02)

---

## 1. 架构评审与最佳路径

### 当前架构洞察

v0.9 建立的 `AssumptionService` 和 `ParameterService` 提供了强大的事实依据（Fact Grounding）。
v0.7 提供的是"骨架"（Base Solution），挑战是如何将 v0.9 的"血肉"（业务假设与参数）
通过一个中间层稳定地注入到 v1.0 的"皮肤"（客户交付物）中。

### 最佳架构路径

**绝对应该从 `Workspace` 中间层数据模型开始开发，而不是直接写文档生成脚本。**

```
workspace_manager.py
  : 维护单个投标项目（Bid Session）的生命周期。
    拉取 v0.7 的业务流和 v0.9 的当前有效假设（Active Assumptions），
    将其锁定为当前版本的快照（Snapshot）。

proposal_engine.py
  : 消费 Workspace 中的快照，利用 LLM 进行文本润色和扩展，
    生成正式报告的各个 Section。

document_renderer.py
  : 纯粹的展现层，负责将生成好的结构化 JSON 渲染为 DOCX/PDF 或提取 PPT 大纲。
```

---

## 2. 技术风险与依赖识别

### 风险1：数据与文本的漂移（Data-Text Drift / 幻觉）

**场景：** `parameter_service` 刚刚将上海仓储的租金指数调整了 5%，
但 LLM 生成的"方案实施"段落里还是旧的成本描述。

**对策：** 在 `proposal_engine` 的 Prompt 设计中，必须强制要求 LLM **引用（Cite）Workspace 中的特定假设版本（Version ID）**，
或者使用**模板插值（Template Interpolation）先固定关键数据，再让 LLM 润色周围的文字。**

### 风险2：上下文窗口溢出（Context Window Limit）

**场景：** 正式报告（摘要/方案/KPI/风险/实施）非常长，一次性把所有内容丢给大模型会导致质量下降。

**对策：** 采用**分块生成（Chunked Generation）架构**。按 Section 独立调用 LLM，最后组装。

### 风险3：依赖关系冲突

**场景：** 用户在生成提案的过程中修改了一个导致冲突的假设（触发了互斥校验）。

**对策：** 系统必须能够**阻断生成并提示用户**。

---

## 3. MVP 优先级与开发顺序

### MVP 核心功能范围（Scope）

1. **Workspace 快照机制**（将 v0.7 + v0.9 绑定为一个投标工程文件）
2. **分模块方案文本生成**（先只做：执行摘要、核心方案、实施计划三个最关键的部分）
3. **单格式导出**（先做 DOCX 导出，因为排版灵活性高，业务人员最容易二次修改）

### 建议的开发顺序

| Step | 模块 | 内容 |
|------|------|------|
| Step 1 | Workspace Context API | 从 AssumptionService 拉取指定 tags 的参数，生成特定项目的 Context JSON |
| Step 2 | Proposal Section Generator | 编写针对单个 Section 的 Prompt 模板，将 Context JSON 注入，实现 LLM 调用逻辑 |
| Step 3 | Document Assembly & Export | 集成 python-docx，将生成的多段文本组装成带基础样式的 Word 文档 |
| Step 4 | *(推迟到 v1.1)* | PPT 大纲自动生成和 PDF 导出 |

## 4. 测试策略

依托于现有的 235+ tests，v1.0 的测试需要转向**状态机测试**和**生成质量评估**。

### 状态一致性测试 (State Consistency Tests)

**用例设计：** 模拟用户在 Workspace 中修改了 `cost_indices.csv` 里的特定区域系数。
断言：`assumption_service` 返回了新版本，Workspace 状态被标记为 "Dirty"（需重新生成），
且重生成的中间层 JSON 包含新数值。

### 数据锚定测试 (Data Grounding / Exact Match Tests)

**用例设计：** 如果传入的假设是 `{"forklift_count": 12, "roi_years": 3}`，
使用正则表达式验证最终输出的 PDF/DOCX 文本段落中，
是否准确无误地包含了这些关键数值，且没有因为 LLM 的幻觉被篡改。

### 组装边界测试 (Assembly Edge-cases)

**用例设计：** 针对分块生成的拼装逻辑，测试生成的"风险"章节和"方案"章节之间是否存在逻辑断层，
确保各章节依赖的是同一个 `version_id` 的假设。

---

## 5. 总结

v0.9 已经打下了非常好的地基。v1.0 的重点不是让 LLM "自由发挥"，
而是用 **Workspace 将底层参数牢牢锁住**，让 LLM 充当一个带有严格"镣铐"的撰稿人。

**建议从构建 `WorkspaceContext` 状态管理类开始敲下第一行代码。**
